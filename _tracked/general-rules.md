## Общие правила — как Клоду работать

Универсальная дисциплина оркестратора: применима независимо от пользователя, машины и проектов. **Портируемо** — этот файл можно скопировать в любую установку Claude Code без правок. Личные правила (идиолект K1, карта среды K2, проектные подсказки) живут отдельно в `~/.claude/CLAUDE.md`.

Подключается через `@local-forks/_tracked/general-rules.md` в `~/.claude/CLAUDE.md` (always-on). Класс знаний для reflect-session — **G** (general); ID-префикс правил — `g-`.

### Algorithm iteration diagnosis gate
<!-- id: g-algo-diagnosis-gate -->
**Trigger:** 2-й вариант алгоритма/формулы тоже даёт неверный результат (та же проблема, другая реализация)
**Action:** до варианта 3 — диагностировать структурную/математическую причину провала варианта 2 и зафиксировать диагноз в ответе; только потом предлагать вариант 3, выведенный из диагноза
**Don't:** продолжать параметрический тюнинг (порог, scale factor) без понимания root cause — это тот же провальный подход с другими числами

### Фиксы базовой линии — отдельный чанк до фичи
<!-- id: g-baseline-fixes-own-chunk -->
**Trigger:** в фича-сессии починены предсуществующие поломки базовой линии (красные тесты, сломанный конфиг/инфра), физически перемешанные с фича-правками
**Action:** оформить фиксы базовой линии отдельным коммитом (в PR-флоу — отдельной веткой от main) ДО или независимо от фича-коммита; при перемешанных ханках — patch-staging (`git add -p` / `git apply --cached`), не бандлить
**Don't:** бандлить фиксы базы в фича-коммит «потому что сцеплены» — следующая ветка от main унаследует красноту, а фиксы недоступны без всей фичи
**Reason:** сессия 2026-06-30 (MeetingRecorder): 4 тест-фикса уехали в RAG-фича-коммит; ветка author-name от main родилась красной, потребовалась пересборка стеком.

### Проектные конвенции → project CLAUDE.md
<!-- id: g-project-conventions -->
**Trigger:** в ходе сессии устанавливаются новые правила/конвенции конкретного проекта (система спрайтов, формат скрипта, архитектура, рабочий процесс)
**Action:** записать в CLAUDE.md проекта (и/или в vault если он является источником правды); auto-memory — опционально как указатель
**Don't:** хранить проектные конвенции только в auto-memory — там их не увидит никто, кто откроет проект

### Проверка staged-диффа перед коммитом
<!-- id: g-staged-diff-check -->
**Trigger:** перед `git commit`, когда стейджишь файл, правленный в сессии
**Action:** `git diff --cached --stat`; если объём заметно больше твоих правок — показать пользователю предсуществующие незакоммиченные изменения и подтвердить, что их тоже коммитим, до коммита
**Don't:** коммитить вслепую — в файле могла быть более ранняя несохранённая работа, которая попадёт в твой коммит молча

### Логический кусок работы → своя ветка + свой PR
<!-- id: g-branch-per-chunk -->
**Trigger:** начинаешь новый логический кусок работы (фича / фикс / батч тюнинга) в репо с PR-флоу
**Action:** до первого коммита куска — `git checkout main && git checkout -b <chunk>`; пушить эту ветку и открывать отдельный PR
**Don't:** досыпать follow-up коммиты в ветку, у которой PR уже открыт — раздувает scope ревью и мешает несвязанные изменения; force-push для переписывания открытого PR запрещён, поэтому ветвиться правильно заранее

### Доменные концепты SQL/DB — verify контекст перед утверждением
<!-- id: g-db-concept-grounding -->
**Trigger:** в reasoning используется доменный концепт SQL/DB engine (lock escalation threshold, query plan operator, isolation level behaviour, default batch size, buffer pool dynamics, MVCC, page split, log flush).
**Action:** перед формулировкой «X означает Y в нашем случае» — верифицировать предпосылки: live table или изолированная staging? shared host или дедикированный? OPTIMIZER plan реальный (через actual hint / DMV) или предположительный? OLTP или OLAP load?
**Don't:** переносить best-practice number (5000 рядов — lock escalation, 8KB — page size, 12K — RCSI threshold) в сценарий без проверки что предпосылка вообще применима.
**Reason:** Сессия 2026-06-27: предложен batch=4500 с обоснованием «5000 — порог lock escalation»; пользователь сразу указал что lock escalation не применим — staging таблица изолирована.

### Δ-rate из двух snapshot'ов — проверить state-reset между ними
<!-- id: g-snapshot-delta-state-reset -->
**Trigger:** agent считает rate как (snap_N − snap_N−1) / Δt для ongoing operation (миграция, backfill, batch job, репликация, queue draining).
**Action:** перед сравнением — verify timeline: происходили ли state-reset events между snap_N−1 и snap_N (cancel+restart, drop/recreate, schema change, service restart, instance failover, fresh staging table)? Если да — snap_N−1 невалиден как baseline; нужен fresh baseline после reset.
**Don't:** брать old snapshot до restart и новый после restart для расчёта rate — даст ~0 или negative rate и ложный ETA.
**Reason:** Сессия 2026-06-27: посчитал «0 rows/sec за 14ч → 70 дней ETA» на клиентской миграции сравнивая snapshot до cancel+restart с snapshot после; пользователь: «так подожди я же перезапускал миграцию и обнулялся прогресс».

### Деструктивный шаг «по аналогии» — проверить накопленный прогресс
<!-- id: g-destructive-step-by-analogy -->
**Trigger:** переносишь шаг (cleanup / drop / reset / wipe / re-copy) из другого контекста/плейбука/фазы в текущий план, и шаг разрушает или обнуляет состояние
**Action:** до включения шага в предложение — проверить, накопил ли текущий контекст необратимый/дорогой прогресс (скопированные строки, частичный бэкфил, скачанные данные, занятая staging-копия), который шаг сотрёт; если да — пометить это явно и выбрать resume/preserve-путь, а не wipe-путь
**Don't:** тащить «очистку» как механический шаг из соседнего сценария — в исходном контексте терять было нечего, в текущем за ним уже стоит часовая необратимая работа

### Инструментируй прежде чем теоретизировать о причине
<!-- id: g-instrument-before-theorize -->
**Trigger:** пользователь сообщает симптом («почему X происходит», «Y меняется/срабатывает не так») у которого нет встроенной атрибуции источника (нет стектрейса/ошибки, указывающих на причину), и ≥2 подсистемы могли его вызвать
**Action:** сначала добавить лог в точке эффекта (TakeDamage / setter / обработчик события) со стектрейсом или именем актора-источника, прогнать, прочитать кто реально вызвал; только потом чинить конкретную подсистему — диагноз выводить из лога, не из гипотезы
**Don't:** теоретизировать и править одну подсистему (геометрия коллайдера, формула) по догадке до того как наблюдение показало источник — в исходной сессии 2 раунда ушло на коллайдер стрелы, а лог `[DMG]`+стектрейс сразу показал что урон идёт от мили-гарда (`EnemyGuard:Update`), стрела ни при чём
